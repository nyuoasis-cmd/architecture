## 5. 🚨 Codex 위임 — 다음에 시킬 사람이 반드시 읽을 것

이 에픽에서 Codex 에 위임했고 **네 번 만에** 성공했다. 실패가 전부 같은 뿌리였다.

### 확정된 제약
| 대상 | 가능? |
|---|---|
| workspaceRoot 안의 **일반 파일** 쓰기 | ✅ 된다 |
| workspaceRoot **밖**(`/home/claude/architecture` 등) 쓰기 | ❌ `Read-only file system` |
| **git 메타데이터**(`.git`) 쓰기 = 브랜치·커밋 | ❌ `index.lock: Read-only file system` |
| 외부 네트워크(`git push`·`gh`) | ❌ `Could not resolve host: github.com` |

🔑 워크트리의 `.git` 은 실체가 아니라 원본 레포를 가리키는 포인터다. 그래서 **파일은 쓰는데 커밋은 못 한다.**

### 그래서 되는 방식 (4차에서 성공한 것)
1. **Codex 에게 git 을 시키지 않는다.** 파일 생성·수정만. 읽기 전용 git 명령(`log`·`status`·`diff`)은 OK.
2. **브랜치·커밋·push·PR 은 사람/Claude 가 한다.**
3. 🚨 여러 PR 로 쪼갤 작업이면 **어느 파일이 어느 PR 소속인지 명단을 남기게 한다**(`CODEX-MANIFEST.md`).
   한 파일이 양쪽에 걸리면 그것도 적게 한다 — 모르고 가르면 한쪽 PR 이 깨진다.
4. **본작업 전 쓰기 검증 한 줄**을 시킨다. 1차는 이걸 안 해서 30분 돌고 빈손이었고, 2차는 **30초**에 잡았다.

### 🚨 보고를 그대로 믿지 말 것
1차 때 Codex 는 «커밋 완료 `4e6f944`»라고 보고했는데 **그 커밋은 어디에도 없었다.**
거짓말이 아니라 `git commit` 이 exit 0 이었고 자기 샌드박스 안에서 본 사실을 말한 것이다 — 그 샌드박스가 폐기됐다.
**완료 보고를 받으면 `git log`·`git status`·파일 존재를 디스크에서 직접 확인하라.**

또 테스트 수를 «18/19»로 보고했는데 실제는 128이었다. 이 레포의 `npm test` 는
**기본 격리에서 파일 단위로 센다**(`--test-isolation=none` 이면 133). 거짓이 아니라 다른 걸 센 것이다.
🔑 숫자는 `ℹ tests N` 줄을 그대로 인용하게 하고, 어느 모드인지 같이 적게 하라.

### Codex 가 찾아낸 것 (브리프에 없던 것 — 위임의 값이 여기 있었다)
- 🚨 **숨은 차단막**: `ContentPanel` 의 `QA_ID_PATTERN` 이 `/^ch(0[1-9]|10)_q…/` 로 **장 범위가 박혀 있었다.**
  이걸 안 고쳤으면 노트를 67개 만들어도 11강 이상은 영영 안 불렸다. PR1 에서 `types.ts` 에
  «장 범위를 정규식에 박지 않는다»고 경고문까지 써 놓고 화면 쪽은 못 봤던 것이다.
- `ch06_q03` — ch01~10 안에서 유일하게 노트가 없던 문항. 「64 + 67 = 131」 셈이 안 맞던 자리.
